0. Đọc phần này trước: bạn không cần “biết kiến trúc” sẵn

Mục tiêu của tài liệu này không phải để bạn đọc xong rồi nhắc lại được câu định nghĩa “Hexagonal Architecture là Ports and Adapters”. Mục tiêu là khi mở một class Java mới, bạn trả lời được: class này đang làm vai trò gì, nó được phép import ai, ai được gọi nó, và nếu đổi công nghệ thì nó có phải sửa không?

Quy tắc học thuật ngữ trong tài liệu này Không cố dịch 100% sang tiếng Việt. Ta giữ từ gốc như port, adapter, application service, transaction boundary, rồi giải nghĩa bằng tiếng Việt tự nhiên. Đây là cách dễ nối kiến thức với code và tài liệu kỹ thuật tiếng Anh hơn.
Sau phần 8
Bạn theo được một HTTP request từ Controller → Port → Service → Adapter → DB.
Sau phần 13
Bạn hiểu vì sao duplicate request/event không tạo tác dụng phụ nhiều lần.
Sau phần 18
Bạn hiểu ArchUnit đang bắt “dependency leakage” như thế nào.
Sau phần 20
Bạn nhìn architecture bằng câu hỏi “đổi tech thì chỗ nào phải thay?”.

1. Bức tranh lớn: Cycle 13 đang cố tách cái gì ra khỏi cái gì?

Một backend service có hai loại thứ rất dễ bị trộn vào nhau:

A. Logic của hệ thống

Ví dụ: tạo sample, chống xử lý trùng, quyết định replay hay conflict, retry outbox, bỏ qua duplicate event.

Đây là phần bạn muốn giữ ổn định.

B. Chi tiết công nghệ

Ví dụ: HTTP/Spring MVC, PostgreSQL/JDBC, Jackson, Micrometer, SLF4J, local event delivery.

Đây là phần có thể thay đổi theo framework/infra.

Mental model: Nếu hôm nay bạn thay PostgreSQL bằng một persistence implementation khác, câu hỏi là “business flow có phải viết lại không?”. Hexagonal Architecture cố làm cho câu trả lời gần với “không; chủ yếu thay adapter ở mép ngoài”.

Đây không phải “Spring/JDBC xấu”. Vấn đề chỉ xuất hiện khi core logic biết quá nhiều về những chi tiết đó.

2. 12 thuật ngữ phải hiểu trước khi đọc code

Boundary
Hiểu là: ranh giới trách nhiệm. Qua ranh giới này, dữ liệu thường được đổi sang “ngôn ngữ” của phía nhận.
Đừng chỉ nhớ: “boundary = đường biên”.
Port
Hiểu là: interface/hợp đồng mô tả một khả năng tại boundary. Nó nói cần làm gì, không nói làm bằng công nghệ nào.
Đừng học máy móc: “port = cổng”. Hình ảnh “cổng” chỉ là ví dụ.
Adapter
Hiểu là: code nối một công nghệ/protocol cụ thể vào một port. Ví dụ Controller nối HTTP vào port IN; JDBC adapter nối port OUT vào PostgreSQL.
Application service
Hiểu là: class điều phối một use case: gọi domain/value object, gọi các ports theo đúng thứ tự, xử lý branch logic ở mức use case.
Domain
Hiểu là: những khái niệm và invariant cốt lõi phải đúng bất kể request đến từ HTTP, test, CLI hay message.
Capability
Hiểu là: “khả năng hệ thống cần/cung cấp”. Ví dụ “persist atomically”, “serialize payload”, “record metric”. Không cần dịch thành một từ duy nhất mỗi lần.
Orchestration
Hiểu là: điều phối thứ tự các bước. Ví dụ validate domain → fingerprint → serialize → persist → record outcome.
Policy vs Detail
Policy: quyết định ở mức cao “hệ thống nên làm gì”. Detail: chi tiết kỹ thuật “làm bằng JDBC/Jackson/Spring như thế nào”.
Dependency
Hiểu là: class A cần biết class/type B để compile. Dependency không chỉ là dòng import.
Dependency Inversion
Hiểu là: core không phụ thuộc implementation ngoài; cả core và implementation gặp nhau tại abstraction/port do phía core định nghĩa.
Composition Root
Hiểu là: nơi duy nhất biết nhiều implementation cụ thể để “lắp” object graph. Trong Cycle 13 đó là SampleFlowConfiguration.
Effect / side effect
Hiểu là: thay đổi có thể quan sát được ở bên ngoài hàm, ví dụ insert DB row, publish event, gửi email. Trong tài liệu này “exactly-once effect” nghĩa là tác dụng nghiệp vụ chỉ được áp dụng một lần.

    // SQL
    // JSON
    // metrics
    // HTTP response

Class trên có ít nhất 5 lý do để đổi:

  • API HTTP contract đổi.
  • Persistence đổi.
  • JSON serializer đổi.
  • Metric/logging stack đổi.
  • Business behavior đổi.
Vấn đề chính không phải “class dài” Vấn đề sâu hơn là dependency direction: logic quan trọng đang phụ thuộc trực tiếp vào những thứ nằm ngoài nó.
Nếu bạn xóa dòng import JdbcTemplate nhưng vẫn viết org.springframework.jdbc.core.JdbcTemplate bằng fully-qualified name, dependency có biến mất không?
Không. Compiler/bytecode vẫn biết type đó.

4. Hexagonal Architecture thực sự là gì?

Có thể tóm bằng một câu: core nói chuyện với thế giới ngoài thông qua các hợp đồng (ports), còn chi tiết công nghệ nằm trong adapters.

HTTP / Spring MVC
→
Port IN
→
Application
→
Port OUT
→
JDBC / PostgreSQL

Vì sao gọi là “hexagonal”?

Hình sáu cạnh chỉ là hình minh họa rằng ứng dụng có nhiều “mặt” giao tiếp. Điều quan trọng không phải số 6. Điều quan trọng là inside/outside và dependency direction.

Ba câu hỏi để nhận ra một thiết kế có tinh thần Hexagonal hay không

  1. Application/domain có import framework/adapter không?
  2. Inbound adapter có gọi qua port IN hay gọi thẳng implementation?
  3. Nếu thay một technology detail, core có phải sửa theo không?

5. Domain / Application / Ports / Adapters / Configuration khác nhau thế nào?

Domain

Nhiệm vụ: giữ invariant và khái niệm cốt lõi.

Ví dụ: IdempotencyKey.

Không nên biết: HTTP, SQL, Spring, Jackson, logging.

Application

Nhiệm vụ: điều phối use case.

Ví dụ: CreateSampleService, LocalOutboxRelay, SampleEventConsumer.

Được biết: domain + ports + Java types.

Ports

Nhiệm vụ: hợp đồng tại boundary.

Ví dụ: CreateSampleUseCase, SampleCommandPersistencePort.

Không nên chứa: ResponseEntity, JdbcTemplate, framework-specific types.

Adapters

Nhiệm vụ: hiện thực việc nói chuyện với công nghệ cụ thể.

Ví dụ: Controller, JDBC adapter, Jackson adapter, observability adapter.

Configuration

Nhiệm vụ: lắp các implementation vào ports.

Ví dụ: SampleFlowConfiguration.

Nó biết nhiều class cụ thể hơn vì đó chính là nhiệm vụ của composition root.

Một class có @RestController và đọc HTTP header thì nên ở đâu?
Inbound adapter. Vì nó nói ngôn ngữ HTTP/Spring MVC.

6. Port IN và Port OUT — phần người mới dễ nhầm nhất

Port IN

Câu hỏi: “Bên ngoài có thể yêu cầu hệ thống làm gì?”

Ví dụ: CreateSampleUseCase mô tả hành động “create sample”.

Controller gọi vào nó.

Port OUT

Câu hỏi: “Application cần thế giới ngoài làm gì giúp nó?”

Ví dụ: persist atomically, serialize payload, deliver event, record metric.

Application gọi ra nó.

Đừng nhớ bằng vị trí file; hãy nhớ bằng hướng của “ý định”

Bên ngoài muốn gọi hệ thống:
HTTP Controller
     |
     v
CreateSampleUseCase       <-- PORT IN
     |
     v
CreateSampleService

Application cần hạ tầng:
CreateSampleService
     |
     v
SampleCommandPersistencePort  <-- PORT OUT
     |
     v
JdbcSampleCommandPersistenceAdapter
Mẹo nhớ rất ngắn IN = request đi vào core.
OUT = core cần đi ra ngoài để hoàn thành công việc.

1
Request vào Controller.
Controller là chỗ được phép biết HTTP header, request body, status code, Jakarta Validation, Spring MVC. Nó đang đứng ở “mép” của hệ thống.
2
Controller kiểm tra wire contract.
Ví dụ: Idempotency-Key đúng format của API, body đúng schema. Đây là validation của giao thức HTTP/API.
3
Controller dịch HTTP DTO → application command.
Từ đây core không cần biết request ban đầu đến từ JSON hay HTTP header.
CreateSampleController.java — ý tưởng quan trọng 
private final CreateSampleUseCase useCase;

var result = useCase.create(
    new CreateSampleCommand(
        key,
        request.purpose().name(),
        request.sampleRequestId(),
        correlationId
    )
);
4
Controller giữ reference kiểu interface CreateSampleUseCase.
Đây là điểm rất quan trọng. Controller biết “hệ thống có capability create sample”, không cần biết class implementation tên là CreateSampleService.
5
Spring runtime đã inject một implementation vào interface đó.
Việc implementation nào được dùng không do Controller quyết định; composition root quyết định.
6
CreateSampleService nhận command.
Nó bắt đầu nói ngôn ngữ application/domain: idempotency key, fingerprint, sample IDs, event data. Không còn HttpServletRequest hay ResponseEntity.

IdempotencyKey idempotencyKey =

        command.purpose(),
        command.sampleRequestId()
    );

PersistSampleResult result =

7
Domain validation vẫn chạy.
Web validation không thay domain invariant. Nếu một ngày use case được gọi từ Kafka/CLI/test, IdempotencyKey vẫn tự bảo vệ quy tắc của nó.
8
Application gọi các port OUT.
Nó yêu cầu “serialize cái này”, “persist atomically cái này”, “record outcome”. Nó không nói “hãy gọi ObjectMapper method X” hay “hãy chạy SQL Y”.
9
Adapters thực hiện yêu cầu bằng công nghệ thật.
Jackson adapter serialize, JDBC adapter chạy SQL/transaction, observability adapter gọi Micrometer/SLF4J.
10
Kết quả quay ngược lại.
Adapter → port result → application result → Controller → HTTP response. Controller mới là nơi dịch result thành status/body của API.
Nếu mai thêm một CLI command cũng muốn create sample, ta có copy CreateSampleService không?
Không. Thêm inbound adapter mới và tiếp tục gọi cùng CreateSampleUseCase.

9. Persistence + transaction: vì sao @Transactional ở adapter lại hợp lý?

Application muốn một khả năng mang ý nghĩa nghiệp vụ: “hãy persist command này một cách atomic”. Nhưng “atomic bằng PostgreSQL transaction + Spring annotation như thế nào” là chi tiết kỹ thuật.

Application nhìn thấy

persistencePort.persist(command)

Nó quan tâm kết quả nghiệp vụ: created / replay / conflict.

JDBC adapter nhìn thấy

@Transactional
public PersistSampleResult persist(...) {
   // SELECT / INSERT / UPDATE ...
}

Nó chịu trách nhiệm dùng transaction thật để đảm bảo atomicity.

Atomicity trong flow này nghĩa là gì?

Với command mới, các thay đổi liên quan như idempotency record, sample row, outbox row và stored response phải commit cùng nhau hoặc rollback cùng nhau. Không được có trạng thái “sample đã có nhưng outbox chưa có” do transaction bị chia sai.

10. Idempotency từ số 0: vì sao cần key + fingerprint?

Vấn đề đời thực

Client gửi request tạo dữ liệu. Response bị timeout nên client không biết server đã xử lý hay chưa. Client retry. Nếu server xử lý như request mới, có thể tạo effect lần hai.

Request 1
Key = K1
Payload = A
Timeout
Client không chắc request đã commit chưa.
Retry
Key = K1
Payload = A
Mục tiêu
Trả lại kết quả cũ, không tạo effect mới.

Ba trường hợp Cycle 13 xử lý

Tình huống Ý nghĩa Kết quả
Key mới Chưa thấy request này Tạo effect/outbox, lưu response, hoàn tất record.
Cùng key + cùng fingerprint Retry đúng request cũ Replay kết quả đã lưu, không tạo effect/outbox mới.
Cùng key + fingerprint khác Client tái sử dụng key cho request khác Conflict IDEMPOTENCY_KEY_REUSED.

Fingerprint dùng để làm gì?

Nếu chỉ lưu key thì server không biết K1 lần hai là retry của payload A hay là một payload B hoàn toàn khác. Fingerprint là digest của canonical request để phân biệt hai trường hợp đó.

Mental model:
Idempotency key trả lời: “client đang nói đây là cùng một logical request”.
Fingerprint trả lời: “server kiểm tra xem nội dung có thật sự là cùng request hay không”.

Scope key được xác định bằng composite key kiểu (actor_scope, operation_name, key_digest), để cùng raw key ở scope/operation khác không bị hiểu nhầm là cùng request.

11. Transactional Outbox: giải quyết “dual-write problem”

Dual-write problem là gì?

Giả sử một command phải làm hai việc:

  1. Ghi business data vào PostgreSQL.
  2. Publish event ra một hệ thống khác.
DB commit, publish lỗi

Business data đã có nhưng event mất. Downstream không biết có thay đổi.

Publish thành công, DB rollback

Downstream thấy event cho một business state thực tế không tồn tại — “event ma”.

Một local DB transaction không tự bao trùm PostgreSQL + external broker. Transactional outbox tránh publish trực tiếp trong command transaction.

Giải pháp

Command transaction:
  INSERT/UPDATE business state
  INSERT outbox_event   <-- "ý định cần publish"
  COMMIT

Sau commit:
  relay đọc outbox_event
  relay deliver event
  relay mark PUBLISHED hoặc FAILED
Điểm quan trọng Outbox row là dữ liệu durable trong cùng database transaction với business change. Vì vậy “business state tồn tại” và “ý định publish event tồn tại” đi cùng nhau.

12. Outbox relay + retry: worker lấy event thế nào mà không đụng nhau?

OutboxRelayUseCase
→
LocalOutboxRelay
→
Persistence Port
→
JDBC claim
→
Delivery Port
→
Local delivery

Flow đơn giản

1
Claim một event đến hạn. Worker cần đánh dấu event là đang được nó xử lý.
2
Deliver. Gọi delivery port.
3
Nếu OK: mark PUBLISHED.
4
Nếu fail: mark FAILED, tính next_attempt_at.
JDBC claim logic — ý nghĩa, không cần thuộc SQL 
SELECT event_id
FROM identity.outbox_event
WHERE next_attempt_at <= now()
  AND (
      status IN ('PENDING', 'FAILED')
      OR (status = 'PROCESSING' AND lease_until < now())
  )
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 1

Giải nghĩa từng ý quan trọng

Cơ chế Ý nghĩa bằng tiếng người
FOR UPDATE Worker đang claim row này trong transaction.
SKIP LOCKED Worker khác gặp row đang bị khóa thì bỏ qua để tìm row khác, không chờ và không claim trùng.
lease_until “Quyền xử lý có hạn sử dụng”. Nếu worker chết, event có thể được worker khác reclaim sau khi lease hết hạn.
attempts Theo dõi đã thử bao nhiêu lần để phục vụ retry/observability.

Backoff + jitter

Cycle 13 dùng backoff tăng theo 1, 2, 4, 8… giây, cap 300 giây, rồi cộng jitter không âm. Backoff tránh retry quá dày; jitter tránh nhiều event/worker cùng thức dậy chính xác một lúc.

13. Inbox + exactly-once effect: delivery có thể lặp, effect vẫn một lần

Hệ thống phân tán thường dễ đạt at-least-once delivery hơn: event có thể được giao lại. Vì vậy consumer không nên giả định “mỗi event chỉ đến đúng một lần”.

Delivery
→
SampleEventHandler
→
SampleEventConsumer
→
InboxPersistencePort
→
JDBC inbox
JdbcInboxPersistenceAdapter.java — ý tưởng cốt lõi 
@Transactional
public boolean recordOnce(OutboxDelivery delivery, Instant receivedAt) {
    int inserted = jdbcTemplate.update(
        "INSERT INTO identity.inbox_receipt ... ON CONFLICT DO NOTHING"
    );

    if (inserted == 0) {
        return false; // event_id đã tồn tại
    }

    jdbcTemplate.update(
        "INSERT INTO identity.identity_profile_sample_effect ..."
    );

    return true;
}

Timeline event đầu tiên

event_id = E1
  -> INSERT inbox_receipt(E1) thành công
  -> INSERT business effect cho E1
  -> COMMIT
  -> applied = true

Timeline duplicate

event_id = E1 lần nữa
  -> INSERT inbox_receipt(E1)
  -> primary key conflict
  -> ON CONFLICT DO NOTHING
  -> inserted == 0
  -> KHÔNG insert effect
  -> applied = false

Nếu receipt insert rồi effect insert lỗi thì sao?

Vì cùng transaction, toàn bộ rollback. Receipt không bị giữ lại sai. Event có thể retry sau đó.

Exactly-once effect ≠ exactly-once delivery Event có thể đến 2, 5 hay 20 lần. Điều ta bảo vệ là business effect chỉ được áp dụng một lần.

14. Runtime call khác source dependency — chỗ rất nhiều người mới nhầm

Runtime: object gọi nhau lúc chương trình chạy

HTTP
  -> Controller
  -> CreateSampleService
  -> JdbcSampleCommandPersistenceAdapter
  -> PostgreSQL

Source dependency: class nào cần biết type nào để compile

Controller ---------------------> CreateSampleUseCase
CreateSampleService ------------> SampleCommandPersistencePort
JdbcPersistenceAdapter ---------> SampleCommandPersistencePort

Hai sơ đồ này nhìn khác nhau vì runtime cần gọi từ core ra adapter, nhưng source code của core không cần biết adapter cụ thể là class nào.

Dependency tồn tại ở những đâu?

  • Field type.
  • Constructor parameter.
  • Method parameter / return type.
  • Annotation.
  • Method call tới type khác.
  • Inheritance / interface implementation.
  • Exception type.
  • Generic type.
Vì vậy “xóa import” không phải là “xóa dependency”. ArchUnit nhìn dependency ở bytecode/type graph, không chỉ nhìn danh sách import ở đầu file.

15. Dependency Inversion — giải thích bằng đúng CreateSampleService

Thiết kế phụ thuộc trực tiếp

CreateSampleService
    |
    v
JdbcSampleCommandPersistenceAdapter
    |
    v
JdbcTemplate / PostgreSQL

Ở đây high-level logic biết low-level implementation. Nếu đổi persistence implementation, application service có nguy cơ phải sửa.

Sau khi đảo dependency

CreateSampleService
    |
    v
SampleCommandPersistencePort   <--- abstraction thuộc boundary của core
    ^
    |
JdbcSampleCommandPersistenceAdapter

Cả application service và adapter cùng phụ thuộc vào port. Adapter “đi vào” hợp đồng của core thay vì core “đi ra” biết adapter.

Từ “inversion” không có nghĩa runtime chạy ngược Nó nói về source-code dependency direction, không phải thứ tự gọi hàm lúc runtime.

16. Composition Root + Spring DI: ai lắp interface với implementation?

Nếu CreateSampleService tự viết new JdbcSampleCommandPersistenceAdapter(...), nó lại biết chi tiết JDBC. Vì vậy việc “chọn implementation nào” được đẩy ra configuration.

SampleFlowConfiguration.java 
@Bean
CreateSampleUseCase createSampleUseCase(
    SampleCommandPersistencePort persistence,
    SamplePayloadSerializerPort serializer,
    SampleCommandObservabilityPort observability
) {
    return new CreateSampleService(
        persistence,
        serializer,
        observability
    );
}

Spring đang làm gì ở runtime?

1
Spring context tìm bean implement SampleCommandPersistencePort.
2
Tìm bean implement serializer port và observability port.
3
Gọi method @Bean với các object đó.
4
Method tạo new CreateSampleService(...).
5
Object được expose dưới contract CreateSampleUseCase.
6
Controller nhận bean đó qua constructor injection.
Mental model: Application service là “thiết bị”. Ports là “ổ cắm”. Adapters là “đầu chuyển”. Configuration là người đứng ngoài chọn đúng đầu chuyển và cắm chúng lại.

17. ArchUnit đọc code thế nào? Không cần chạy application

Đây là phần quan trọng nếu trước đây bạn thấy câu “ArchUnit bắt dependency leakage” hơi mơ hồ. 

Source code
   |
   | mvn/test compile
   v
.class bytecode
   |
   v
ClassFileImporter
   |
   v
JavaClasses
   |
   v
ArchRule
   |
   v
rule.check(PRODUCTION_CLASSES)
   |
   +--> PASS
   |
   +--> AssertionError + dependency vi phạm

Bước 1 — Java đã compile thành bytecode

ArchUnit không cần boot Spring. Nó đọc metadata trong các .class đã compile: class nào có field type gì, method gọi type gì, annotation gì, implement interface nào…

Bước 2 — ClassFileImporter import các class

Nó xây một mô hình các class trong package cần kiểm tra.

Bước 3 — JavaClasses là “bản đồ type/dependency”

Hãy tưởng tượng mỗi class là một node, dependency là các mũi tên. 

CreateSampleService
   |--> IdempotencyKey
   |--> SampleCommandPersistencePort
   |--> SamplePayloadSerializerPort

JdbcSampleCommandPersistenceAdapter
   |--> SampleCommandPersistencePort
   |--> JdbcTemplate
   |--> Transactional

Bước 4 — ArchRule hỏi trên bản đồ đó

Ví dụ một rule có ý nghĩa:

"Classes trong application
 không được phụ thuộc vào Spring/JDBC/Jackson/Micrometer/SLF4J"

Bước 5 — Nếu một field JDBC lọt vào application?

package ...application.sample;

public class CreateSampleService {
    private final JdbcTemplate jdbcTemplate;
}

Dù không chạy app, ArchUnit vẫn thấy mũi tên: CreateSampleService -> org.springframework.jdbc.core.JdbcTemplate.

Đây là lý do architecture test mạnh hơn code review bằng mắt Rule chạy tự động mỗi lần test. Một developer mới vô tình import framework vào core có thể bị chặn ngay.

18. ArchitectureTest của Cycle 13 bảo vệ những gì?

Rule Giải thích dễ hiểu
Domain không phụ thuộc adapter/framework Invariant không được biết Spring, servlet, persistence, logging.
Application không phụ thuộc framework/adapter Use-case orchestration không import JDBC/JPA/Jackson/Micrometer/SLF4J/Spring.
Ports technology-independent Interface không biến thành API riêng của framework.
Inbound adapters dùng inbound ports Controller không gọi thẳng CreateSampleService.
Top-level packages không tạo cycle Tránh vòng phụ thuộc khiến package A/B/C biết lẫn nhau.

Tại sao còn cần fixture cố tình sai?

Một architecture test xanh chưa chắc rule tốt; có thể nó scan sai package và chẳng kiểm tra gì. Vì vậy fixture cố ý tạo vi phạm, ví dụ application import JdbcTemplate. Test phải chứng minh rule thật sự bắt được lỗi đó.

So sánh dễ nhớ: Architecture rule là đầu báo khói. Negative fixture là nút “TEST” trên đầu báo — bấm vào để chứng minh còi thật sự kêu.

19. TDD + evidence: Cycle 13 kiểm chứng behavior thế nào?

Red → Green → Refactor dùng cho branching behavior

Bước Ý nghĩa thực tế
Red Viết test cho behavior chưa có; test fail đúng lý do.
Green Viết implementation tối thiểu để behavior pass.
Refactor Dọn cấu trúc mà giữ behavior xanh.

Không phải thứ gì cũng cần “ép TDD hình thức”

Wiring/configuration phù hợp hơn với context/configuration tests. Boundaries phù hợp với ArchUnit. SQL/transaction/concurrency cần Testcontainers trên PostgreSQL thật.

Các lớp bằng chứng

  • Application unit tests: new command, replay, fingerprint conflict, relay success/failure/backoff, inbox duplicate.
  • Serializer tests: mapping response/event ổn định.
  • Observability tests: recorded/replayed, relay attempted/published/failed, inbox applied/duplicate.
  • Configuration test: ports được lắp vào đúng application implementations.
  • Architecture tests: boundaries và negative fixtures.
  • Testcontainers: atomic persistence, rollback, concurrent duplicate, duplicate delivery, expired lease, DB role behavior trên PostgreSQL thật.

20. Đổi công nghệ thì sửa đâu? Đây là bài test giá trị nhất của boundary

Thay đổi Chủ yếu phải sửa Phần nên giữ ổn

Boundary tốt không hứa “không bao giờ sửa code” Nó giúp khoanh vùng phần phải sửa và giảm hiệu ứng dây chuyền.

21. Người mới nên đọc repo theo thứ tự nào?

  1. Đọc CreateSampleUseCase trước. Chỉ hỏi: system cho phép caller yêu cầu gì?
  2. Đọc Command/Result. Application boundary dùng dữ liệu gì?
  3. Đọc CreateSampleController. HTTP được dịch vào command ra sao?
  4. Đọc CreateSampleService. Đánh dấu từng dependency là domain hay port OUT.
  5. Đọc từng port OUT. Mỗi port mô tả capability gì?
  6. Sau đó mới đọc adapters. Xem JDBC/Jackson/Micrometer hiện thực capability đó thế nào.
  7. Đọc SampleFlowConfiguration. Xem object graph được lắp ra sao.
  8. Đọc LocalOutboxRelay. Tập trung state machine + retry.
  9. Đọc SampleEventConsumer. Tập trung duplicate handling.
  10. Cuối cùng đọc ArchUnit + Testcontainers. Xem architecture/transaction được chứng minh thế nào.

Mỗi lần mở một class, tự hỏi 7 câu

  1. Class này nhận input từ ai?
  2. Nó trả output cho ai?
  3. Nó chứa business decision hay technology detail?
  4. Dependencies trong constructor là domain, port hay framework?
  5. Nếu đổi HTTP/DB/serializer thì class này có cần đổi không?
  6. Nó có đang gọi qua interface đúng boundary không?
  7. Test phù hợp là unit, architecture, configuration hay integration?

22. FAQ cho người mới

Có phải cứ thấy interface là port?

Không. Port phải đại diện một capability có ý nghĩa tại boundary. Tạo interface cho mọi class chỉ làm code dài hơn.

Domain và application khác nhau thế nào?

Domain giữ invariant/khái niệm cốt lõi. Application điều phối một use case bằng domain + ports. Domain mỏng trong một sample flow nhỏ là bình thường.

Vì sao Controller không gọi thẳng CreateSampleService?

Vì Controller nên phụ thuộc vào capability contract CreateSampleUseCase, không vào implementation cụ thể. Như vậy adapter không “biết quá sâu” vào core.

Vì sao application không dùng ObjectMapper trực tiếp?

Vì serialization là technology detail. Application chỉ cần capability “serialize payload”; adapter quyết định Jackson hay implementation nào.

Có thể đặt @Service lên CreateSampleService không?

Về kỹ thuật có thể, nhưng Cycle 13 chủ động giữ application thuần Java và tạo bean tại composition root để boundary rõ hơn và unit test dễ hơn.

Transaction là business logic hay technical detail?

“Phải atomic” có thể là requirement của use case; nhưng cách hiện thực bằng Spring transaction/PostgreSQL là technical detail của persistence adapter.

Outbox có làm delivery đúng một lần không?

Không tự động. Outbox giúp không mất “ý định publish”. Delivery vẫn có thể lặp; inbox/dedup phía consumer bảo vệ exactly-once effect.

Hexagonal có phải Clean Architecture không?

Chúng có tinh thần gần nhau về dependency direction và tách core khỏi details, nhưng thuật ngữ/layering không hoàn toàn đồng nhất. Đừng cố map 1:1 mọi tên gọi.

1. Nếu thêm Kafka consumer để create sample, class mới nằm đâu?

Inbound adapter phụ thuộc implementation cụ thể thay vì capability contract.

24. Glossary chuẩn: giữ từ gốc, giải nghĩa tự nhiên

Thuật ngữ Cách nên hiểu Tránh hiểu quá máy móc
Boundary Ranh giới trách nhiệm/ngôn ngữ giữa hai vùng. Không chỉ là “đường biên vật lý”.
Port Interface/hợp đồng cho một capability tại boundary. Không cần dịch thành “cổng” trong mọi câu.
Adapter Code nối technology/protocol cụ thể với port. Không chỉ là “bộ chuyển đổi” theo nghĩa phần cứng.
Inbound / driving side Phía kích hoạt use case của application. Không cần ép dịch “bên lái”.
Outbound / driven side Phía application cần gọi để hoàn thành use case. Không cần ép dịch “bị lái”.
Application service Class điều phối use case. Không đồng nghĩa với “Spring @Service”.
Domain invariant Quy tắc phải luôn đúng trong domain. Không chỉ là validation của HTTP.
Dependency Inversion Core và detail gặp nhau qua abstraction phía core. Không phải runtime call chạy ngược.
Composition Root Nơi tạo và nối object graph. Không phải business service.
Idempotency Retry cùng logical request không tạo thêm effect. Không có nghĩa mọi request giống nhau đều trả cùng kết quả nếu payload khác.
Fingerprint Digest của canonical request để phát hiện key reuse sai. Không phải raw request body tùy ý.
Transactional Outbox Business change + durable publish intent trong cùng DB transaction. Không có nghĩa broker publish nằm trong cùng DB transaction.
Inbox deduplication Receipt unique giúp duplicate event không áp dụng effect lần hai. Không ngăn transport gửi duplicate.
Lease Quyền xử lý có thời hạn để reclaim sau crash. Không phải database lock kéo dài vô hạn.
Adapter leakage Technology detail rò vào domain/application/ports. Không phải memory leak.
Atomicity Một nhóm thay đổi commit cùng nhau hoặc rollback cùng nhau. Không đồng nghĩa với “thread-safe” nói chung.
Exactly-once effect Tác dụng nghiệp vụ được áp dụng một lần dù delivery có thể lặp. Không khẳng định network chỉ deliver một lần.
